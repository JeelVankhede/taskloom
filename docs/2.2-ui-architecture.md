# Task 2.2: UI State and Component Architecture

```
TaskBoardPage
├── FilterBar
├── SummaryPanel
│   ├── StatCards          total, open, overdue, closed
│   └── PriorityChart      tasks by priority
├── Board
│   └── Column             one per status, virtualized
│       └── TaskCard       opens TaskDetailPane (?task=ENG-12)
└── NewTaskDialog
```

**Server state and UI state are separate.** Server data lives in Apollo Client's normalized cache. Filters are UI state. They live in the URL search params through a `useTaskFilters` hook, so a filtered board survives a reload and can be shared as a link.

**One hook owns the data.** `useTaskBoard(filters)` runs the board and the summary in one operation with one filter value, so they share a snapshot and never disagree. Cards, stats, the chart, and the filter bar receive props and render on their own in tests; only a column's later pages and the detail pane fetch.

**Columns page on their own.** Each column calls `fetchMore` with its own cursor as it nears its end, and renders only the cards in view. A long Done column does not slow the others.

**The chart always shows every priority.** `PriorityChart` is an MUI X Charts bar chart of the five priorities, including None. The API zero-fills priorities, so the axis never shifts between filters.

**Every region handles its own states.**

- **Loading.** Skeleton columns and stat cards shaped like the final layout, so nothing jumps when data arrives.
- **Error.** The message and a retry: the board and summary reload together; a failed column page retries alone.
- **Empty.** Two cases. A project with no tasks shows a plain message. A filter with no matches offers to clear the filters.
