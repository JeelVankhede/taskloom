# Task 2.2: UI State and Component Architecture

```
TaskBoardPage
├── FilterBar
├── SummaryPanel
│   ├── StatCards          total, open, overdue
│   └── PriorityChart      tasks by priority
└── Board
    └── Column             one per status
        └── TaskCard
```

**Server state and UI state are separate.** Server data lives in Apollo Client's normalized cache. Filters are UI state. They live in the URL search params through a `useTaskFilters` hook, so a filtered board survives a reload and can be shared as a link.

**One hook owns the data.** `useTaskBoard(filters)` runs the board query and the summary query with the same filter variables, so the two views never disagree about scope. Components receive data as props and hold no fetch logic. Each one renders on its own in tests.

**Columns page on their own.** Each column calls `fetchMore` with its own cursor. A long Done column does not slow the other columns.

**The chart always shows every priority.** `PriorityChart` is a Recharts bar chart of the five priorities, including None. The API zero-fills priorities, so the axis never shifts between filters.

**Every region handles its own states.**

- **Loading.** Skeleton columns and stat cards shaped like the final layout, so nothing jumps when data arrives.
- **Error.** The message and a retry button that refetches only the failed query.
- **Empty.** Two cases. A project with no tasks shows a plain message. A filter with no matches offers to clear the filters.
