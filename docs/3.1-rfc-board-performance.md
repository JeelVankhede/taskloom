# RFC: Task Board Performance for Large Projects

| Field | Value |
|---|---|
| Status | Proposed |
| Author | Jeel |
| Audience | Engineering team, product manager |
| Date | September 2026 |

## 1. Problem

The platform serves 500+ organizations. Users report that the task board becomes unusable for projects with 2,000+ tasks. Page loads take 6 to 8 seconds, and every interaction repeats that cost.

The current board works in one pattern:

1. One GraphQL query fetches every task in the project.
2. The client renders every card on the Kanban board.
3. Every filter change or status update refetches everything.
4. A drag-and-drop reorder triggers the same full refetch.

Every step scales with project size. The first three rows below are estimates to confirm in week 1. The last two follow directly from the current design.

| Cost | Estimate at 2,000 tasks | Why it grows |
|---|---|---|
| Response size | About 2 MB of JSON, at about 1 KB per task with assignee, labels, and status | Linear in task count |
| SQL statements | Up to 6,000 if nested fields resolve per task without batching | Linear in task count times nested fields |
| Client render | 2,000 cards in one commit | DOM size, layout, and paint |
| Time per drag | A full reload, 6 to 8 seconds | Every move repeats the full load |
| Board shown to other users | Stale until they reload | No change feed |

The users hit hardest are those on the largest projects.

## 2. Goals and Non-Goals

**Goals.** Board load time independent of project size. A drag writes one row and triggers no refetch. Filters run on the server. Statistics match the visible board.

**Non-goals.** Realtime multi-user sync. Offline use. Search.

## 3. Options

### Option A: Optimize the client, keep the query

Virtualize columns so only visible cards render. Memoize cards. Move the data into a normalized client cache. Apply moves optimistically. Debounce filter input.

- **For.** No API change. Ships in about a week.
- **Against.** The payload, the SQL cost, and the first load stay linear in project size. A 20,000-task project is still slow, and 100x growth breaks it.

### Option B: Paged board API

The server returns the first page of every column in one round trip. Each column loads more on its own cursor. Filters apply on the server. The summary is a separate query with the same filter. A move writes one row and returns the moved task, and the client updates its cache in place.

- **For.** Cost is columns times page size, not project size. A move costs one row write. The list and summary stay consistent.
- **Against.** New API surface. The client must handle moves between partially loaded columns. A drop on a filtered board can land between hidden cards. Rank keys need occasional rebalancing.

### Option C: Local-first sync

The client keeps the whole project in local storage and syncs changes through a change feed.

- **For.** Every interaction is instant after the first sync. It also enables realtime and offline use.
- **Against.** It needs a change feed, a sync protocol, and conflict handling. The first sync is still linear in project size. It is months of work.

A server-side response cache was also considered and rejected. Every write invalidates it, and filter combinations make the hit rate low.

### Comparison

| Criterion | A: Client only | B: Paged API | C: Local-first |
|---|---|---|---|
| First load cost | Linear in tasks | Columns × page size | Linear, first sync only |
| Cost of a move | Mutation plus local update | One row write | Local, then synced |
| Filter change | Local, over all tasks | One server query | Local |
| Holds at 100x | No | Yes | Yes, with sync work |
| Effort | 1 week | 3 to 4 weeks | Months |

## 4. Recommendation

Adopt Option B, plus the virtualization and optimistic updates from Option A. B removes the linear cost on the server. A's client work removes the remaining render cost inside long columns. Option C stays on the roadmap for when realtime becomes a product goal.

**Board query.** One statement loads the first 50 cards of every column. Each column is an ordered range scan on the `(org_id, project_id, status_id, rank)` index, so the database never sorts the project.

**Load more.** A column requests its next page with `rank > cursor`. Rank is unique per project, so the cursor is complete.

**Filters.** Filters live in the URL and run on the server through one filter input shared by the board and the summary. A new filter cancels the in-flight request.

**Summary.** One SQL statement with `GROUPING SETS` returns totals, overdue, and the breakdowns by status, priority, and assignee. The board and the summary run in one read-only snapshot, so they always agree.

**Move.** `moveTask(taskId, statusId, afterTaskId, beforeTaskId)`. The client sends neighbor ids, never a position. The server generates a rank between the neighbors, writes one row, and returns the task. The client moves the card before the response arrives and reconciles when it does. The summary refetches once, debounced, after moves settle.

**Batching.** Nested fields resolve through request-scoped DataLoaders. A CI test counts SQL statements for the board query and fails above a fixed ceiling.

## 5. Performance Targets

Targets are proposals. Phase 0 confirms them against the measured baseline.

| Metric | Target |
|---|---|
| Board query, server p95 | 300 ms at 2,000 tasks; 500 ms at 20,000 |
| Board time to interactive, p95 | 1.5 s |
| First-load payload | Under 200 KB, whatever the project size |
| SQL statements per board request | 8 or fewer, whatever the project size |
| Filter change, end to end, p95 | 500 ms |
| Drag: card moves on screen | Within one frame |
| Drag: server acknowledgment, p95 | 150 ms, with zero board refetches |
| Summary query, p95 | 150 ms |
| Move failures after one retry | Under 0.1% |

## 6. Implementation Plan

The estimates assume two engineers.

| Phase | Week | Work |
|---|---|---|
| 0. Baseline | 1 | Instrument resolver timings, SQL statements per request, payload bytes, and client time to interactive. Group dashboards by project size. |
| 1. Server | 2 | Board query, per-column pagination, summary, DataLoaders. Build new indexes concurrently. Backfill ranks per org if the current order is stored differently. |
| 2. Client | 3 | New board behind a flag: normalized cache, column virtualization, server-side filters, loading, error, and empty states. |
| 3. Moves | 4 | `moveTask` with server ranks, optimistic updates, and the rank rebalance job. |
| 4. Rollout | 5 onward | Section 7 |

## 7. Rollout

**Additive API.** The new board, summary, and move fields ship next to the current query. The current query keeps working until the last client moves off it.

**Per-org flag.** The client chooses the old or new board by a feature flag per organization. Turning the flag off returns an org to the old board at once. Both boards read and write the same task rows, so switching back loses nothing.

**Data first.** If ranks need a backfill, it runs per org in its own transaction. An org's flag turns on only after a check confirms that every task in that org has a rank.

**Stages.**

1. Internal organization.
2. 10% of organizations, weighted toward projects with 2,000+ tasks, where the gain is largest.
3. All organizations with large projects.
4. Everyone.

Each stage needs three days that meet the targets in section 5, an error rate no higher than the old board, and no support tickets about wrong ordering. Otherwise the flag goes off and the stage repeats after a fix.

**Contract.** The old full-fetch query is deprecated once every org is on the new board. It is removed two releases later.

## 8. Risks and Open Questions

| Risk | Response |
|---|---|
| A drop on a filtered board can land between hidden cards | Accepted. The order among visible cards is always correct. |
| Rank keys grow under heavy reordering | Rebalance when a key passes 64 characters. It takes a short exclusive project lock, so it runs in the background. |
| The drop target's neighbors are not loaded yet | The client sends only visible neighbor ids. The server ranks between them. |
| Other users see changes only on reload | Accepted for this RFC. Realtime needs the change feed from Option C. |

**Open for product.** Is 50 cards per column the right first page? Should the Done column show only recent closures by default?
