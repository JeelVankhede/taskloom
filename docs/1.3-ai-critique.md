# Task 1.3: AI Critique of SPEC v1.1

This is the AI critique output, reproduced verbatim. It reviewed SPEC_FINAL v1.1. Finding ids (N, C, S, X, I, F) are referenced by [1.3-analysis.md](1.3-analysis.md).

---

**Verdict.** The tenancy core, derived-column model, and activity design are sound. The defects cluster in six places: a permissive RLS policy that undermines role lookup, two invariants the spec claims are enforced in the database but are not, a global `users` table with no RLS and an UPDATE grant, no index for the default task sort, unbounded GraphQL cost, and re-key by transfer, which is the most expensive design in the spec and is not required by the brief.

Inputs: SPEC_FINAL v1.1 plus the DDL in SPEC.md v1.0, because v1.1 carries no DDL. Findings against DDL assume the v1.1 Prisma migrations reproduce it. Severity reflects impact at the stated scale, not effort.

## 1. N+1 query risks

**N1. Nested connections under list fields (High).** `Task.comments`, `Task.timeline`, and `Project.activity` are paginated connections reachable from `tasks` and `organization.projects`. DataLoader batches keys. It cannot apply a per-parent `LIMIT`. A 50-card page that asks for `timeline(first: 5)` becomes 50 `UNION ALL` queries, and each one probes every activity partition since that task was created. **Fix:** a validation rule that rejects these fields under a list path, so they resolve only under `task(id)` or `project(id)`. If list access is ever needed, batch with `LATERAL (... LIMIT n)` over `task_id = ANY($ids)`.

**N2. The loader surface is larger than contract 5 implies (High).** A board card needs project (for `identifier`, and since v1.1 for `isOverdue`, which depends on project state), status, assignee, labels, and comment count. An activity event needs actor, `from` and `to` users, `StatusSnapshot.current`, `LabelSnapshot.current`, `ProjectSnapshot.current` with its successor hop, the comment, and the task. Summary rows need status and assignee. "Every nested field from a list is batched" is a rule with no enforcement, and one missed field ships an N+1. **Fix:** an explicit loader registry (users, membership by user, project by id with successor resolution, status, label, labels by task, comment count by task, comment, task) and a CI test that counts SQL statements for a canonical board query and fails above a fixed ceiling.

**N3. Authorization per resolver (Medium).** `authorize(capability)` runs per resolver. If it reads the membership row, a list of 50 mutable items costs 50 reads. **Fix:** read the membership once in the request lifecycle, store the role in context, and make `authorize` a pure function of that role.

## 2. Data consistency

**C1. Flipping a closed status to open fails on `ASSIGNEE_INACTIVE` (High).** `statuses_sync_task_closed` updates `is_closed` on every task in the status. For each closed task assigned to a deactivated member (closed tasks keep their assignee by C6.3), `tasks_guard_assignee` sees `OLD.is_closed AND NOT NEW.is_closed`, reads the membership, and raises. One departed member in the Done column blocks the workflow edit, with an error that names an assignee the admin never touched. The spec's claim that reopen clears an inactive assignee in the same statement is false on this path. **Fix:** move the flip into a procedure, `app.set_status_closed_kind`, shaped like `archive_status`: it clears inactive assignees on reopened tasks and returns them for one `task.assignee_changed` event each. A trigger cannot do this without violating principle 5.

**C2. "An archived status has no tasks" is enforced only from the status side (High).** `assert_status_valid` fires on `UPDATE OF archived_at, closed_kind` on `project_statuses`. `tasks_derive_closed` checks that a status exists in the project, not that it is live. `updateTask(statusId: <archived>)` therefore succeeds in the database. There is also a race: `archive_status` holds `FOR UPDATE` on the status, a concurrent `moveTask` waits on the FK key-share lock, then commits a task into the status that was just archived. **Fix:** `tasks_derive_closed` reads `archived_at` with `FOR SHARE` whenever `status_id` changes and raises a new `STATUS_ARCHIVED`. `FOR SHARE` conflicts with the archive's no-key update, so the race closes. Apply the same `FOR SHARE` to the archived-label guard.

**C3. Activity `from` values race under READ COMMITTED (High).** The API reads the current value, updates, and writes `from, to`. Two concurrent status changes A to B and A to C both record `from: A`. The history is permanently wrong, and history is never migrated. **Fix:** PostgreSQL 18 `UPDATE ... RETURNING OLD.status_id, NEW.status_id`. Prisma cannot express `RETURNING OLD`, so task mutations need `$queryRaw`, or a `SELECT ... FOR UPDATE` before the update. Label diffs need the same treatment.

**C4. Summary and list read different snapshots (Medium).** C12 guarantees that breakdowns sum to `total` inside one statement. Outcome 5, "statistics always match the visible board", spans two root fields. Under READ COMMITTED each statement takes a new snapshot. **Fix:** run read-only requests as `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, which costs almost nothing in PostgreSQL.

**C5. Keyset pagination on nullable and mutable sort keys (Medium).** `DUE_DATE` and `PRIORITY` are nullable. A row comparison `(due_date, id) > ($d, $id)` yields NULL for undated rows, so they vanish, and a cursor that encodes a NULL returns nothing. `UPDATED_AT` changes during pagination, so rows skip or repeat. **Fix:** sort on `(due_date IS NULL, due_date, id)` and `(coalesce(priority, 5), id)` with the null flag encoded in the cursor. Keep `UPDATED_AT` as a documented best-effort order or drop it.

**C6. `closed_at` cannot back any metric (Medium).** Flips never stamp it, and R1's hiding rule leaks: own close at T1, flip to open, flip back to closed, and the API returns `closedAt = T1` with `isClosed = true` for a task that was open in between. Any "completed this week" or cycle-time chart built on `closed_at` is wrong. **Fix:** a flip to open sets `closed_at = NULL`. That is not backdating, so D5's intent survives. Derive metrics from `task.status_changed` events.

**C7. Writes into read-only archived projects (Medium).** Deactivation clears assignments in archived projects, and auto-archive selects closed tasks in archived projects. The second one falsifies "restoring the project restores exactly what was visible before". **Fix:** auto-archive excludes non-active projects. Document deactivation as the one intended exception, because the assignee invariant outranks read-only.

**C8. One event per mutation has no database backstop (Medium).** Jobs, backfills, and operator SQL can mutate tasks without writing history. **Fix:** the task repository sets `app.audited = on` in the transaction, and a statement-level `AFTER` trigger on `tasks` raises when it is absent for `app_user` and `app_jobs`. An operator must set it deliberately and own the consequence.

**C9. `rekey_project` changes constraint mode for the rest of the transaction (Low).** `SET CONSTRAINTS ALL IMMEDIATE` fires every deferred check the caller had pending and leaves `INITIALLY DEFERRED` constraints immediate afterwards. A later two-statement ownership transfer in the same request then fails. **Fix:** name the constraints, or require re-key to run alone in its transaction.

**C10. No optimistic concurrency (Low, scope).** Concurrent description edits are last-write-wins with no conflict signal. A `version integer` checked in the `UPDATE ... WHERE` closes it and is additive.

## 3. Scalability at 100x

Assumptions: today about 500 orgs × 20,000 tasks = 10M tasks and about 15 events per task. At 100x that is about 1B tasks, 15B events, and single projects of 200,000 tasks.

**S1. `tasks` is unpartitioned while history is (High).** D10 partitions activity from day one because converting later is a full copy. The same argument applies to `tasks` at 1B rows with 11 indexes: vacuum, index rebuilds, and bloat all operate on one relation. Every PK and unique constraint already leads with `org_id`, so hash partitioning by `org_id` (for example 32 or 64 partitions) needs no key change today. The same property makes a later move to a distributed Postgres with `org_id` as the distribution column cheap. Decide now, or record why not.

**S2. One Prisma interactive transaction per request (High).** The request holds a PgBouncer server connection for its entire duration, including resolver CPU time. Queries inside a Prisma interactive transaction execute sequentially, so DataLoader batches do not overlap, and the default transaction timeout is 5 s. Required pool size becomes RPS × request latency. **Fix:** no external I/O inside the transaction, explicit `timeout` and `maxWait`, and server-connection hold time p95 as a tracked metric.

**S3. O(n) single-transaction rewrites on large projects (High).** Re-key, status flip, status archive, and rank rebalance each rewrite up to 200,000 rows. `project_id` sits in seven of the task indexes, so re-key rewrites nearly every index entry, and deferred FK and unique checks then run at commit. "Seconds" understates it. Tens of seconds of project lock, a WAL spike, and replica lag are the realistic range, to be measured. **Fix:** F1 removes re-key entirely. Flip and archive are rare and can stay with a UI warning. For rebalance, making rank unique per `(project, status)` allows per-column rebalances. `archive_status` would then regenerate ranks for the moved tasks, which it already visits.

**S4. Hot parent rows (Medium).** Every task FK check and every explicit move lock takes `FOR KEY SHARE` on the project row. Every event insert takes a key share on the actor's membership row, and the assignee guard takes `FOR SHARE` on it. Many concurrent lockers on one row create MultiXacts, a known contention point under concurrent writes to one hot project. **Fix:** load-test a single project with concurrent moves and watch MultiXact wait events before scaling decisions. Drop the explicit move lock if the FK key share already provides the rebalance exclusion. It does, because rebalance takes `FOR UPDATE`.

**S5. History at 15B rows (Medium).** Monthly partitions are shared by all tenants. The first page of an org or project feed has no lower time bound, so it probes every partition ever created. An org purge becomes scattered deletes across every partition. **Fix:** bound feeds with a lookback window plus explicit "load older", and schedule purges with a rate limit.

**S6. The aggregate escalation cannot serve the contract (Medium).** `project_status_counts` answers only the unfiltered by-status breakdown. The summary accepts the full filter. Overdue changes at local midnight with no write, so it can never be a maintained counter. The real hotspot at 100x is the org-level summary with no project filter. **Fix:** an unfiltered project header reads counters plus an overdue count from a partial index (I4). Filtered summaries stay query-time. Org-level summaries accept only indexable filters such as `assigneeIds = [me]`.

**S7. Done columns grow without bound (Medium).** Auto-archive defaults off, so at 100x closed tasks are the majority of every board index and every filtered scan of a closed column. **Fix:** default auto-archive on (for example 90 days), or render closed columns limited to recent closures.

**S8. UUIDv7 locality claim (Low).** With PK `(org_id, id)`, inserts land at one point per org, not at one right edge. This is still better than v4. D13's rationale should say so.

## 4. Security

**X1. Permissive `own_read` and `member_read` leak into tenant-scoped queries (High).** Permissive policies combine with OR. With `app.org_id = X`, a query on `org_memberships` returns `org_id = X OR user_id = me`. A role lookup that relies on RLS for the org filter, such as `findFirst({ where: { userId } })`, can return the user's owner role from org Y while they are a viewer in X. The layer whose only job is to catch a missing filter fails on the exact table that drives authorization. **Fix:** scope the cross-tenant policies to the switcher phase: `USING (user_id = app.current_user_id() AND app.current_org_id() IS NULL)`, and the same for `member_read`.

**X2. `users` is global, unprotected, and writable (High).** It has no RLS, and `app_user` holds `UPDATE` on every column. A resolver bug with a wrong `WHERE` can rewrite any platform user's `email` or `auth_subject`, which is account takeover across tenants. Every email on the platform is readable by the runtime role. `addMember(email)` gives any org owner, and anyone can create an org, an account-existence oracle. **Fix:** RLS on `users` so SELECT covers self plus users with an active membership in the current org, and UPDATE covers self only. Revoke UPDATE on `auth_subject`. Run email lookup through a `SECURITY DEFINER` function that returns an id and a uniform response, with a rate limit. Expose `User.email` to admins and self only.

**X3. Unbounded query cost (High).** `first: Int` has no maximum, `organization.projects` is unpaginated, and nesting is unbounded (task to project to activity to snapshot to project to activity). **Fix:** cap `first` at 100 in validation, add depth and cost limits, and use persisted queries for the first-party client.

**X4. Tenant context is forgeable by any SQL the API runs (Medium).** `app_user` can call `set_config`. With SQL injection the chain is: set `app.user_id` to any id from the global `users` table, read that user's org ids through `member_read`, set `app.org_id`, read everything. RLS here defends against missing filters, not injection. The spec should state that threat model. **Fix:** lint bans on `$queryRawUnsafe` and `$executeRawUnsafe`. If injection is in scope, use an HMAC-signed context verified inside a `SECURITY DEFINER` `current_org_id()`. Independently, write policies as `org_id = (SELECT app.current_org_id())` so the function evaluates once per query as an initplan instead of per row in non-index filters.

**X5. Attribution is supplied by the API (Medium).** `actor_id`, `created_by`, and `deleted_by` come from resolver code, so the audit trail is only as honest as every resolver. **Fix:** `DEFAULT app.current_user_id()` and a trigger requiring `actor_id = app.current_user_id()` when `actor_kind = 'user'` under `app_user`.

**X6. Privileged columns the database does not guard (Medium).** `app_user` can UPDATE `org_memberships.role`, so one bug promotes anyone to owner, and the database checks only `LAST_OWNER`. Task numbers allocate only when the inserted value is 0: an insert with an explicit number above the counter breaks creation in that project permanently, because the counter reaches the taken number, the insert hits the unique violation, the rollback restores the counter, and every later create repeats it. **Fix:** the insert trigger always allocates and rejects a supplied value. Role changes go through a definer function that checks the caller's role from context.

**X7. Fail-closed reads are silent (Medium).** Code that uses the root Prisma client instead of the request transaction, or a job without context, reads zero rows and reports success. **Fix:** construct the root client with a role that has no table grants, so misuse errors loudly.

**X8. Soft-deleted orgs rely on the API alone (Low).** No policy checks `deleted_at`, and `member_read` shows deleted orgs in the switcher. **Fix:** add `deleted_at IS NULL` to `member_read`. Restoration needs its own path (F2).

## 5. Missing indexes and denormalization

**I1. The default sort has no index (High).** `tasks` defaults to `CREATED_AT DESC`, and no task index contains `created_at`. Every default list query on a 200,000-task project reads the whole filtered set for a top-N sort. `PRIORITY` ordering has the same gap. **Fix:** make the default `id DESC`, since UUIDv7 is creation order, with `(org_id, project_id, id DESC) WHERE archived_at IS NULL`, and add `(org_id, project_id, coalesce(priority, 5), id)` for priority order.

**I2. Label filters scan org-wide (Medium).** `task_labels_by_label (org_id, label_id, task_id)` has no project. An org-wide "bug" label on 1M tasks is fully scanned to filter one board. **Fix:** denormalize `project_id` into `task_labels`, index `(org_id, project_id, label_id, task_id)`, and update it in cross-project move and re-key, both of which already rewrite rows in that scope.

**I3. `tasks_auto_archive` disables HOT updates (Medium).** `updated_at` changes on every edit, and this index is the only one that contains it. Dropping it makes title, description, and priority edits, the most frequent ones, HOT-eligible. The nightly job then scans closed live rows per org through `tasks_board` filtered to closed status ids, which costs the size of the Done columns once a day.

**I4. Per-project overdue count (Medium).** `tasks_project_due` includes closed tasks, and past-dated closed tasks dominate a mature project, so a board-header overdue count scans them all. **Fix:** `(org_id, project_id, due_date) WHERE archived_at IS NULL AND NOT is_closed AND due_date IS NOT NULL`.

**I5. Unindexed FK columns referencing memberships (Low).** `created_by`, `author_id`, `deleted_by`, and `actor_id` are harmless while memberships are never deleted. At purge, each membership delete runs an FK check across the org's rows, which are dead tuples by then. **Fix:** purge children first and vacuum before deleting memberships.

**Do not denormalize** comment counts or identifiers. A grouped loader over `comments_live_count` for one page is cheap, and a stored identifier breaks on re-key.

## 6. Flow misconfiguration and scope

**F1. Re-key by transfer should be a key-history table (High).** A re-key changes the project UUID. Every stored `projectId` (client cache, URLs, `TaskFilter.projectIds`, future saved views and webhooks) breaks or needs successor resolution in every resolver. `tasks(filter: { projectIds: [oldId] })` returns an empty board silently. Activity splits across tombstones, and S3 applies in full. **Fix:** `project_keys (org_id, key, project_id, retired_at)` with PK `(org_id, key)`. A re-key becomes two row writes. The project id and all history stay stable. Resolution is one lookup. Tombstones, successor chains, chain flattening, `PROJECT_REKEYED`, and most of T9 disappear. Principle 4 still holds: the id is the identity, and keys are never reused.

**F2. `restoreOrganization` is unreachable (High).** The request lifecycle returns `NOT_FOUND` for a soft-deleted org before tenant context is set, so the mutation can never run. **Fix:** a dedicated root mutation that verifies an owner membership through `own_read`, then sets context only for the restore.

**F3. The viewer role will be scored as an authorization gap (Medium).** The brief lists "viewer". Reviewers read that as read-only. A viewer that creates, moves, and archives tasks reads as a missing check, not a product choice, however well D4 documents it. **Fix:** viewer is read-only, with comments at most. Add a `contributor` role later if needed. Adding an enum value is metadata-only.

**F4. Prisma defaults contradict the model (Medium).** Prisma defaults optional relations to `onDelete: SetNull` and all relations to `onUpdate: Cascade`. On a composite FK, `SET NULL` targets `org_id` too and fails the NOT NULL. Relation `disconnect` on a composite optional relation can try to null `orgId`. The zero-drift gate (T13) may report the monthly partitions as drift, which would fail CI every month. **Fix:** explicit `onDelete: NoAction, onUpdate: NoAction` on every relation, scalar writes (`assigneeId: null`) instead of `disconnect`, and a T13 run after the partition job has created future partitions, to confirm before relying on it.

**F5. Cross-project move and aliases are outside the brief (Medium).** They carry alias rows, number reallocation, rank regeneration, two-project locking, and event scoping rules. Deferring them costs nothing later: numbers are never reused, so aliases can start at the first move ever made, with no backfill.

**F6. Operational surface (Medium).** Five database roles, a discovery function, soft delete with a 30-day purge, and auto-archive are all defensible, but none is asked for. **Fix:** keep `app_owner`, `app_user`, and one jobs role. Move the purge and discovery design to a "designed, not built" appendix.

**F7. User provisioning is unspecified (Low).** The only write to the global table, just-in-time creation on first login, has no flow, no uniqueness race handling on `auth_subject`, and no statement of which role performs it.

**F8. Overall scope (High, for the assessment).** The spec is roughly twice the surface the brief requires, and Part 2 will exercise perhaps a fifth of it. Reviewers score Impact and Direction. Design that the implementation never touches reads as unverified, and it buries the strong parts: three-layer isolation, derived columns with invariant tests, typed history, and the one-statement summary. Keep those, the board and rank flow, and the summary. Everything in F1, F4, F5, and F6 becomes an appendix with its additive path.
